# Design notes

Why rook-mon-dns works the way it does. For usage see the [README](../README.md).

## Problem

Ceph clients outside the Kubernetes cluster (Proxmox, bare-metal hosts, VMs)
need the monitor addresses. With Rook these addresses live in the
`rook-ceph-mon-endpoints` ConfigMap and change whenever a mon moves to another
node. Hard-coding IPs in every client breaks on the next failover.

## Data source

```yaml
data:
  # mon endpoints; with hostNetwork these are the node IPs (port per mon)
  data: g=192.168.1.103:6789,l=192.168.1.105:6789,j=192.168.1.107:3300
  # mon -> node assignment with the node IPs: this is what we publish
  mapping: '{"node":{"g":{"Name":"node-01","Hostname":"node-01","Address":"192.168.1.103"}, ...}}'
```

- The operator publishes the node IPs from `mapping`. They are only reachable
  if Rook runs the mons with `hostNetwork: true`. In that case the IPs in
  `data` equal the node IPs; if they differ (ClusterIPs, pod network), the
  operator sets `Ready=False` (`HostNetworkRequired`) and publishes nothing.
  It deliberately never falls back to ClusterIPs.
- Limitation: hostNetwork mons bound to another node IP than the one in
  `mapping` (multi-NIC, `network.addressRanges`) are also rejected.
- The mon port is taken from `data` per mon (default 6789). Whether Ceph
  clients handle msgr2-only (3300) ports in SRV records is not clearly
  documented upstream; point clients at `mon-all` if in doubt.
- If the ConfigMap is briefly broken (empty or invalid mapping, missing
  ConfigMap), the last published records are kept and only `Ready` turns
  `False`. Losing all mon DNS during a failover is worse than a stale entry.

## Record names

Mon IDs (`g`, `j`, `l`, ...) are assigned by Rook and change on failover, so
they make poor DNS names. The operator sorts mons by ID and publishes
`mon1`..`monN` (template `recordTemplate`, `{n}` or `{id}`), plus an aggregate
`mon-all` record with all IPs and an optional `_ceph-mon._tcp` SRV record.

Caveat: the numbering follows the sort order, so when a mon is replaced the
numbers of the other mons can shift. Clients should use `mon-all` or the SRV
record; `monN` names are for humans and monitoring. Use `{id}` in the
template if you need names tied to a specific mon.

## Why ExternalDNS `DNSEndpoint`

The operator writes one `DNSEndpoint` per `CephMonDNSEndpoint` and lets
ExternalDNS (`--source=crd`) talk to the DNS provider. The operator therefore
needs no DNS credentials and works with every provider ExternalDNS supports.
The `DNSEndpoint` Go types are mirrored in `internal/externaldns` because
external-dns does not publish them as an importable module.

## Security model

Publishing DNS records is powerful (DNS hijacking), so the operator is kept
narrow:

- **Namespaced only.** The source ConfigMap and the `DNSEndpoint` always live
  in the CR's namespace; the API has no fields to point elsewhere.
- **Never touch foreign objects.** An existing `DNSEndpoint` with the CR's
  name that the CR does not own is neither updated nor deleted
  (`DNSEndpointConflict`).
- **Zone allowlist.** `--allowed-zones` rejects other zones (`ZoneNotAllowed`)
  and removes the records the CR published before.
- **No ClusterRoles at runtime.** One Role per watched namespace
  (`--watch-namespaces`); the CRD is the only cluster-scoped object.
  `config/rbac/role.yaml` is generated by controller-gen from the RBAC markers
  and is not deployed.
- **Hardened pod.** PSS `restricted`, distroless image, memory limit, no CPU
  limit, NetworkPolicies (egress only to the API server ports 443/6443 and
  cluster DNS). The API server rule is port-based: CNIs evaluate egress after
  the service IP was translated, so a service-CIDR rule would block it.
  NetworkPolicies need an enforcing CNI (e.g. Cilium, Calico; not Flannel).
- **Fail fast.** The manager checks at startup that the `DNSEndpoint` CRD is
  installed.

## Out of scope (for now)

- Rook versions without the `mapping` field.
- Cross-namespace references.
